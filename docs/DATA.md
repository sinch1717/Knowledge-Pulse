# Where the data comes from

This is the part of the project most likely to be challenged in a review, so it is worth being precise
about it.

## The problem

The system mines a conversation archive. A newly built system has no archive. Clustering needs a few
hundred questions before the topics mean anything, and the trend and emergence analysis in F4 needs at
least three reporting periods to compare — otherwise there is no "previous period" and every topic is
new by definition.

Waiting for real traffic is not an option on a project timeline. So the conversation archive is
generated, and the generation procedure is documented here because it is a limitation that has to be
stated, not hidden.

## What is real and what is not

**The knowledge base is real.** A public documentation site is crawled and indexed exactly as it would be
in production. No synthetic documents.

**The questions are synthetic.** Generated by an LLM prompted to write in the voice of customers using
that product, with instructions to produce short, informal, sometimes misspelt text rather than
well-formed queries — because Sentence-BERT's behaviour on messy short text is one of the open questions
this project is examining (see [L5] in the report's literature survey).

**The retrieval, the confidence scores, the clustering and the ranking are all real.** Once a synthetic
question enters the pipeline it is treated identically to a real one. Nothing downstream is faked.

## Generation procedure

1. **Crawl** the chosen documentation site. Record page count, chunk count and the crawl date.
2. **Derive a topic frame** from the actual site structure: roughly 15–20 subjects customers plausibly ask
   about, taken from the headings rather than invented.
3. **Plant three kinds of gap** on purpose, so there is something for the analytics to find:
   - Topics the docs genuinely do not cover, which should produce low retrieval confidence.
   - Topics the docs cover well and that many people ask about, which should become FAQ candidates.
   - One topic that starts at near-zero volume in period 1 and spikes in period 3, which is the emerging
     concern the system is supposed to catch. If it does not catch this, F4 is not working.
4. **Generate around 800 questions** distributed across three simulated monthly periods, with volumes per
   topic drawn from a long-tailed distribution rather than spread evenly, because real support traffic is
   never uniform.
5. **Replay** every question through the live chat endpoint so the conversation log is populated by the
   real system rather than written directly into the database. This matters: it means the confidence
   scores in the log were genuinely computed, not assigned.
6. **Hold out 50 questions** with reference answers written by hand from the source pages. These never
   enter the conversation log. They exist only for the RAGAS evaluation in F6.

Every generated question is stored with a `synthetic: true` flag and the prompt version that produced
it, so the corpus can be regenerated or audited later.

## Limitations, stated plainly

- Synthetic questions are cleaner and more grammatical than real ones even when the prompt asks for mess.
  Real support text contains more fragments, more context-free follow-ups and more frustration.
- The topic distribution reflects what the generating model thinks customers would ask, not what they
  actually ask. Volume rankings are therefore only as good as that assumption.
- Because gaps were planted deliberately, the system finding them is a check that the pipeline works,
  not evidence that it would find unknown gaps in the wild.
- There is a circularity risk in using an LLM to generate the questions and an LLM to name the resulting
  clusters. Cluster labels should be spot-checked by hand against member questions.

## What would strengthen the paper

A small real pilot alongside the synthetic run. Even 150–200 genuine questions from a live deployment —
a college department site, a student club, a local business willing to embed the widget for a fortnight
— would let the paper report the synthetic results as the main experiment and the real results as a
sanity check. That comparison is worth considerably more than a larger synthetic set.

Worth deciding early, because a two-week pilot has to start two weeks before you need the data.
